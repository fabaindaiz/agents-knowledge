## 5. Topic-based reading against today

`release.py report` estimates tokens as characters/4, which it says runs about 1.4 times low. The coding
session's base read is 10.1k tokens. The index is 6.3k tokens: the action table 4k, the phase
table 1.1k, and the rest about 1.2k. A card is about 220 tokens (median 877 bytes, largest 1.4k).

| Request | Today | Topic-based (router ≈1.2k + slice ≈550 per topic) |
|---|---:|---:|
| Typo or rename (step 0 consults nothing) | 10.1k | 10.1k |
| A retry in a service: 2 cards | 10.1 + 6.3 + 0.4 = **16.8k** | 10.1 + 1.2 + 0.55 + 0.4 = **12.3k** |
| The same, plus one card of another topic by cue | 17.0k | 12.5k |
| A change touching two topics: 4 cards | 17.2k | 13.1k |
| A review of a wide diff, or a harvest | 6.3k index | unchanged: reads every slice |

The saving is about 4k per request that consults the index, roughly 2/3 of the index. **Loading the
topic's method sections whole would cancel it.** The checks topic alone carries 2.3k, and boundaries
carries 2k. The topic should name those sections as pointers to read at the step that needs them; the
cut planned in `d-5ed7e8-ef478f` decides what stays in the base.

## 6. What topic-based export would risk

The test: a carrier that does not receive topic T loses every note in T whose recorded occurrences
include that carrier's domain.

| Topic | Cross-domain | Domains in its occurrences | Risk if dropped |
|---|---:|---|---|
| absence, copies, checks | 5/7, 4/6, 7/7 | all seven | **Never drop.** Every domain has met them |
| effects | 5/6 | web, embedded, client, mobile, tooling | High. A "no network" carrier still meets it in local imports and actuator reports |
| versions | 5/5 | web, data, mobile, client, tooling | High. On-device files outlive builds |
| measurement | 5/7 | analytics, web, embedded, client, mobile, tooling | High |
| environment | 3/4 | tooling, analytics, web, mobile | High for any carrier with a gate |
| time | 2/6 | renderer, embedded, mobile, analytics | **The trap.** Four as-of notes look analytics-only, but the topic also holds the owner's cross-domain case. Dropping it from a non-analytics carrier loses the clock cards |
| boundaries | **0/5** | web, analytics, client (one source each) | **Unverifiable.** No note has a second domain, so the test cannot pass or fail. Treat it as needed everywhere until it can |

The cross-domain counts do not support dropping any topic for any carrier today. What the data supports
is dropping single notes whose own occurrences sit in one domain with two or more independent sources,
and no note meets that bar yet.

## 7. Questions for the owner

1. **One primary topic per note, with cross-topic reach by cue only**, or several topics per note?
   *Recommended: one primary.* The slice and the export stay a partition, and nothing is duplicated.
   The price is that the cues of the about 15 cross-topic notes need maintaining.
2. **Record each occurrence's domain as a field** (for example `seen_in: [web-service, embedded]`,
   kinds only, checked by the build), or keep a one-off hand classification like this one?
   *Recommended: the field.* §6's test then becomes a build check rather than a reading. The price is
   one pass over 53 notes and a line per future occurrence.
3. **Cross-domain cues with a test.** For each note, keep a few requests phrased in another domain
   where it occurs, and have `check` require that each reaches the note. *Recommended: yes, starting
   with the owner's clock case.*
4. **Export defaults to everything.** A topic leaves a carrier only when the carrier declines it in
   `carrier.toml`, and never by inference from its domain. *Recommended: yes, until question 2's field
   exists and a topic shows a single domain with two or more independent sources.*
5. **Nine topics, or eight with `environment` folded into `checks`?** *Recommended: nine.* "Can it
   fail" and "where did it run" have separate remedies, and four notes justify their own slice.
