# A check must be seen to fail

## Why it works

A check has two ways to be green: nothing is wrong, or the check cannot see. From the outside they are identical, and the second is common, because checks are glue — a command piped into a filter, a count grepped from a log, a chain of steps where one exit code stops the rest. Every link in that glue can silently turn the check into a constant.

The only way to tell the two greens apart is to make the thing wrong on purpose and watch the check notice: plant the violation, see red, remove it, see green. This is what mutation testing does for unit tests; it applies with more force to CI plumbing, audits and data filters, which nobody tests at all.

**The plant is the defect the check exists for, applied to the real artefact**: remove the guard, delete the line that installs it in the real host, not a change to how the guard behaves. A check that finds its subjects in the code under test cannot see that plant, because the defect removes the subject from what it finds: a sweep that asks whether every guarded route refuses the unprivileged caller, and finds the guarded routes in the registry the guard fills, passes when the guard is deleted; a guard tested on a host the test builds for itself passes when the real host stops installing it. Anchor the expected set outside the code under test and compare it both ways, and test the guard on the real composed host. And count by implementation, not by subject: a subject tested through a mirror on the consumer's side leaves this implementation's check unseen.

A related failure hides inside chains: **stacked failures hide each other.** When step 2 fails, steps 3 and 4 never run, and whatever is wrong with them is invisible until step 2 is fixed. A gate that "fails" is not evidence that its later steps pass. The same holds inside one test: only its first failing assertion was seen red, and the assertions after it go green when the code is fixed without ever having failed. See each one fail, or mutate each guard separately.

Two more forms of the same constant, both common in tools that were never meant to be gates. **An exit code is not a verdict**: an interpreter that reports a compile error, carries on and exits 0 turns every run into a pass, so the glue has to read the output for the tool's own error markers. And **"identical" needs a negative control**: a comparison that finds no difference proves something only once a deliberately different input has been seen to differ. Two runs that share an uncontrolled variable cannot disagree on it: two builds inside the same second agree on every embedded timestamp by accident, so a reproducibility check separates its runs by more than the timestamp's resolution, or varies the clock (`reproduce-the-checkout-not-only-the-environment`). Likewise a probe of state that persists passes at any instant after the event, so a probe meant to pin *when* something happened is bracketed with the state just before, and seen by mutation to tell the two apart. A refusal test, too, asserts each refusal's *reason*, not only how many there were — the count can be right while every reason after the first is wrong.

**A check that was seen red once can still go blind** with no change to itself: its subjects disappear — a folder it scans is retired, a marker it searches for is renamed. Guarding against that is a property of every run rather than of the wiring, and it is `report-coverage-before-findings`: count the subjects, and fail on zero. **Partial blindness is not zero**: compare the count a check examined with the number of subjects known to exist, because a check that recognises half of them passes every plant placed in the half it sees. A probe of a subject that has already gone can likewise read a stale initial value and pass. A completion check has the same shape here: its *false* answer must be distinguishable from silence — the command's own exit status, not the pipe's; an empty match treated as unknown, not as clean.

## When it does NOT apply

Checks whose detection is already proven by an external conformance suite — and even then, the local wiring that runs them can still swallow the output, so the plant-and-watch is still owed once per wiring. Where nothing outside the code can say what the subjects should be (the registry is itself the specification), a check drawn from the code verifies the wiring only, and says so.

## What it costs

One planted-violation run per new check, usually minutes. It is skipped because the check "obviously" works, which is exactly the belief it exists to test.

## Where it came from

A typecheck gate in CI piped the tool's standard output into a log and counted errors in it. With the option that installs missing stubs, the tool printed its errors to **standard error** — a single line on stdout against dozens on stderr — so the count was zero on every run and the gate could not fail. In the same change, the local chain *audit, lint, typecheck, test* stopped at the typecheck's exit code and **never ran a test**, while the documentation said it did. When the chain was later rebuilt on the lowest supported interpreter, **every module failed to import** because of an annotation the newer interpreter evaluates lazily — hidden until then because the gate had died at the typecheck first: three stacked causes, each hiding the next.

The same discipline recurs in that repository as tests whose names say they prove the strict check can detect a violation, guards verified by deleting what they guard and watching them name it, and an audit check that caught a stale document on its first run.

A second repository — an interactive renderer whose engine can also run headless — met the exit-code form twice. On a compile error the engine printed the error and a cascade of script errors, carried on, and **exited 0**, so a measurement probe with a broken script produced output that looked like a measurement; the runner now fails any run whose output carries the error marker. Later the whole gate was **green and blind**: a stale class cache left several classes unresolved, the validator failed to load, and the script error did not fail the run. The cause — a stale cache read in place of its source — is covered by `derived-copy-goes-stale-silently`; what belongs here is that the gate could not go red. The same repository records the negative-control form: a packaged texture rendered the same frames as the built-in copy, and only swapping in a different image proved the packaged one was drawn at all; and a package verifier reported every file after a bad one as bad too — the refusal count was right and the reasons were not. Its checks are introduced by breaking them: an emptied table cell and an over-long caption each turned red the checks that watch them.

A third repository — an offline-search application with a packaging toolchain — met the completion form in one session: three completion checks answered *done* wrongly. `echo "EXIT=$status"` after a pipe printed 0 over a failed build, an empty log filter was read as a clean probe rather than a dead receiver, and a transfer monitor declared three packs complete while the last was 53 of 314 MB in, because an unescaped `.` in the pattern matched the partial file whose existence means the opposite. The same repository's zero-subjects occurrences are counted in `report-coverage-before-findings`.

## Literature

- **DeMillo, Lipton & Sayward, 1978, ["Hints on Test Data Selection: Help for the Practicing Programmer"](https://doi.org/10.1109/C-M.1978.218136)** (IEEE Computer 11(4)). *Bibliographic record verified 2026-09-23; the full text was not opened.* Mutation testing: plant faults to measure whether tests detect them. **What we take:** detection is measured, not assumed. **Where we go further:** applied to gates, audits, pipelines and filters, where there is no test framework to host the mutant.
- **Jia & Harman, 2011, "An Analysis and Survey of the Development of Mutation Testing"** (IEEE Transactions on Software Engineering 37(5)). *Cited from a carrier's proposal; not checked against the source here.* A suite is judged by whether it detects planted faults, so it is only as strong as the faults planted. **What we take:** the plant has to be the defect the check is for.
- **reproducible-builds.org, "Timestamps", and the reprotest manual.** *Checked by a carrier 2026-10-05.* Timestamps are named the largest source of irreproducibility and a fixed epoch passed in the environment is the remedy; reprotest varies the clock between its two builds. Neither states the same-second trap in words; it is the reason the time variation exists. **What we take:** the remedy for two runs that cannot disagree.

## Evidence

**Measured in three repositories:** in the first, errors sent to the stream the gate did not read, a chain that ran no tests, and an import failure in every module hidden behind it; in the second, a compile error that exited 0 and a gate that stayed green with classes unresolved; in the third, three completion checks whose *false* could not be told from silence, one of them a monitor that matched its own partial file.

**2026-10-03 — four occurrences and one run, from the bundle's home and an app repository with an on-device test suite.**
- **Zero subjects after a layout moved.** When a bundle release moved what the carriers' own audits read, the audits that checked the knowledge index found zero notes and zero links in at least two repositories, and passed, while the same release turned hundreds of their other checks red and drew the attention away. Each was repointed, made to fail on zero and planted against again. This folds the queued `split-a-checked-file-and-the-check-goes-blind`: a check names the files it reads, so moving or splitting them leaves it green on nothing; its own occurrence, in a data-analysis repository, was an index split by area that left the audit reading the original file alone, so a dead link and a note removed from its area were both invisible until the check was taught the new files and seen red on both.
- **Zero tests is not a pass.** A device-test run on a degraded emulator ran zero tests and nothing flagged it; the session noticed only because it read the results. A runner's verdict is read from the count of tests run and failed.
- **A threshold's cut sits between a measured good and a measured bad.** Four times in one repository's rendering and settings tests, an assertion passed with the defect present: a threshold within a few percent of the defective value, a "drawn in this region" test, a coarse colour property that passed an inverted image, a settings test with no positive control. The negative-control clause extends from equality to thresholds: measure the defect and the fix, put the cut between them with a margin, keep both numbers beside the assertion. That boundary sentence waits for a second repository.
- **Plant the idiomatic spelling, not only the canonical one.** In the same repository every invariant check of a text-scanning audit had been seen red on its own plant, and each missed the spelling the codebase actually uses (five idioms of the language and the build tool). Seen to fail has to mean seen to fail on that spelling. Just et al., FSE 2014, on mutants resembling real faults, is cited from the proposal and *not checked against the source*.
- **The census, run once, statically.** Over one repository's audit of about fifteen checks, each required to have a planted-failure test, every check but one had one; the exception was the check that delegates to the bundle's verifier and trusts its exit code — the local wiring this note's boundary names. The census's own first count was wrong (it recognised only assertions on a count), so the measuring script needed its own planted case. Verdict: confirms (`experiments.md`, *Run*).

**2026-09-30 and 2026-10-01 — the census executed, in two repositories.** In the third repository above, the validator's reporter was instrumented to record the call site of every check and the whole suite run once: about a third of the check sites had ever been seen red, more than half were exercised and never red, and about a tenth were never reached, so **about two in three had never been observed to fail**. The never-red set was not the periphery: it held the format and normalisation versions, the payload codec, the dictionary hash and the link between the text index and its entries; most of the unreached sites were report-a-failure branches in error paths, which is where a plant would enter. Counting by call site rather than by subject is what showed it. In a small web service whose gate was built in one session, every one of its checks (about ten) was seen red in the end, but one, the record-id check, had passed with no errors for a whole session while recognising none of the definitions it existed to check, so duplicate detection over about two thirds of the ids was silently off; a heading template and the tool that read it disagreed on where the id sits. It was noticed only because the count of definitions found was lower than the number of ids written. Moved, it turned red at once on several real double definitions. The same gate had one red for the wrong reason, an assertion on a framework's internal list that an upgrade made lazy. Together these run the experiment below.

**2026-10 — the plant has to be the defect, in the same web service.** A role sweep found the privileged routes by reading the set a decorator fills, and its planned see-it-fail step was to delete the decorator from one method: the one plant this design cannot turn red. A task review flagged it; the derived set was replaced by a table of every writing method and its role in the decisions document, which the test parses and compares both ways with the registry. In the same branch, two pieces of request middleware were tested on an application the tests built, and a whole-branch review found that deleting either installation line in the real application failed no test; a test on the real application now covers both. The hand-kept-list side of the same question, from another repository, is in `report-coverage-before-findings`.

**2026-10 — inside one test, and probes of persistent state, in a code-generator repository.** Two assertions sat behind a failing one in a test written first; when the code made the first pass, the other two were green without ever having been red, and were checked afterwards by mutating each guard. A behaviour spec still passed with its probe moved one step earlier, because the probed cell kept its value; it now also probes that the next cell is still empty one step before, which a mutation shows it tells apart. A probe of a program that had already stopped read the start-up listing and passed; the runner now reads the last listing and fails when nothing runs. Three more occurrences of the note in the same period confirm it, without a new form.

**2026-09 — two runs that could not disagree, in a document repository.** Two builds of a fixed-layout document run in quick succession were byte-identical, and the session nearly recorded that pinning the visible date made the output reproducible. Built a second or two apart, they differed in a creation-time metadata field while rendering identically; pinning that timestamp to the commit's time made separated builds identical. A decision row had already stated the wrong conclusion and was corrected; what caught it was a closing review that spaced the two builds on purpose.

What would generalise it: for every check in a gate, record whether a planted violation was ever observed turning it red, and count how many never were. Run once statically and executed in two repositories (above). What would still move it: the same executed census in a gate older than this note, where nothing was built with it in mind.

**2026-09-24, offered at 0.0.29 — the same blindness in one more carrier, and two more checks over zero subjects.** When a release moved the notes into state folders, that carrier's index check globbed the old folder, compared two empty sets and stayed green. A triage of its other checks then found a layer-direction check matching a module prefix no import used (green since written; fixed, it reported a few dozen upward imports) and a migration check matching a substring anywhere in a function (it counted about a seventh of a registry as declaring its guard where only a couple did).
