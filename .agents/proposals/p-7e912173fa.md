A permission rule on files exists to catch an edit a session makes as a by-product, never to stop intended work. So `deny` goes only on a file that only a tool writes (a checksum list the build regenerates); `ask` goes on generated files and on the guards (hooks, settings, git hooks), so an intended change passes with one confirmation and an accidental one is seen; and originals, incoming material, the carrier's own fields and proposals get no rule. Because a deny at any scope wins over an allow, an exception is made by leaving a path without a rule, never by allowing it; and a host may consult path rules for its edit tool only, so each rule is written for that tool.

## Evidence

2026-10-08, two repositories. A carrier whose edit denies covered every path the release ships could replace its bundle only by a shell copy, which its update procedure never names (that carrier's update, finding 7). The same day the home, which had no rules at all, walked its paths one by one with its owner: a deny on the checksum list, asks on the generated content, the installed skills and agents and the guards, and no rule on originals, incoming material or proposals, the owner's reason being that a block should not stop creating or editing incoming material or local changes meant to be integrated.
