# Proposal: a-gate-is-pruned-as-well-as-grown

A gate grows and is never pruned. Every incident adds a check, every regression adds a test, and nothing in the
process ever asks whether a check still earns its seconds: there is a rung for adding a control and none for
retiring one. The cost is not paid once. A gate is chained to every commit, so its duration multiplies by the
number of times a day the work is committed, and it is the step between finishing a task and being able to close
it — which makes it the step an agent is most tempted to skip, narrow or run on a subset, and each of those is a
way of not having run the gate at all. So the gate's own cost belongs inside the work, not outside it: a release
or a close measures how long its gate took and what the time bought, and a check that has never been red in a
counted window, or that fails only where another already fails, is a candidate for removal with the same standing
as a candidate for addition. The asymmetry to correct is that adding a check needs an incident and removing one
needs nobody's permission, so nobody does it.

## Evidence

Measured in one owner's repositories, counted as one source, on 2026-11-24: four gates of comparable projects run
the same day took on the order of one to two minutes each, over suites of several hundred to about a thousand
tests, and one reported more warnings than tests. The bundle's own suite is of the same order. None of those
repositories has ever removed a check: their histories show additions and baselines raised, never a retirement,
and two of them carry ratchet baselines in the thousands of findings, which is the same growth in another form.
No measurement of redundancy: what would settle it is a counted run over one suite — for each check, when it was
last red, and how many of its failures are already covered by another check that fails first. The ordered-gate
case is already queued as its own candidate, which bears on this one: a gate that stops at the first red step
never exercises the steps after it, so a redundant check can sit green-by-omission for a long time and nobody
notices. Literature: none consulted; what to read is the work on test-suite minimisation and on flaky and
obsolete tests, which has standard measures for exactly this and would say whether removal by coverage overlap is
safe in practice.
