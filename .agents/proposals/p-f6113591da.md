# Proposal: a-guarantee-stops-at-its-own-boundary

A stronger guarantee does not reach past the component that gives it, and moves a duty onto the application: a stream engine's exactly-once covers its own state, so an external sink still needs a transactional or idempotent write; a serializable isolation level makes the application retry whole transactions on serialization failures; a failed file sync may leave the kernel marking the pages clean, so a second sync succeeds over lost data and the failure is fatal for that data, not retryable. The usual answer, "turn the guarantee on", is wrong at that boundary. It stops applying where the sink is idempotent by key, the engine serialises by locking, or the filesystem keeps failed pages dirty. The check: crash a worker mid-checkpoint and compare sink and source counts; run a write-skew load test and track the serialization-failure rate; inject an I/O fault under a write-then-sync test.

## Evidence

A stream engine's post on end-to-end exactly-once (2018), summary; a relational engine's documentation on transaction isolation; LWN, *PostgreSQL's fsync() surprise* (2018), snippets. Borders the candidate an-idempotence-key-coarser-than-the-write-unit-drops-data.
